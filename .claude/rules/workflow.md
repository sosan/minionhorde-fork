## Tier 0: Direct Response Workflow

### Trigger
- ≤3 existing files to modify (verify with Glob)
- No new dependencies, no API/interface changes, no auth/DB/critical logic touched, no new business logic
- OR explicit user flag: "direct", "rápido", "sin pipeline"

### Agents Activated

| Agent | Mode |
|-------|------|
| Project Manager | Detection + confirmation via AskUserQuestion |
| Developer | Direct implementation (no TDD, no docs) |
| Test | Optional — run existing tests if they exist |
| DevOps | Git commit (conventional) + push + changelog |

### Documents Created

**None.** Tier 0 generates 0 documentation (no PRD, no specs, no planning).

### Branch

`direct/<short-desc>` — see §Feature Branch Policy.

### TDD Protocol

Optional. Only if existing tests exist — Developer runs them for regression. No new tests created by Test.

### Rollback Protocol

Minimal. Stashpoint only (no backup branch). See §Rollback Protocol §Naming Convention.

### File Integrity Checkpoints

| Delegation | Verify BEFORE | Verify AFTER | Recovery |
|------------|---------------|--------------|----------|
| Tier 0 Ph 1 — Developer: implementation | Task description exists | Modified files exist + content >0 | Developer |
| Tier 0 Ph 2 — Test: regression (optional) | Existing tests exist | Tests PASS | Developer |
| Tier 0 Ph 3 — DevOps: commit | Phase 2 verified or skipped | Commit exists + CHANGELOG entry | DevOps |

### Escalation

If during Tier 0 task is more complex:
1. PM re-assesses via §Complexity Assessment
2. May escalate to Tier 1/2/3
3. Branch changes: `direct/<slug>` → `feature/<slug>` or `fix/<slug>`

## Feature Branch Policy

Every workflow creates and works on an isolated feature branch. No implementation on default branch.

| Tier | Format | Example |
|------|--------|---------|
| Tier 0 direct | `direct/<short-desc>` | `direct/fix-typos` |
| Tier 1 new-project | `feature/<project-slug>` | `feature/task-api` |
| Tier 2 feature addition | `feature/<feature-slug>` | `feature/oauth2-login` |
| Tier 3 bug fix | `fix/<ticket-number>-<short-desc>` | `fix/142-token-refresh` |

**When to Create:** Tier 0 Phase 0 (after user confirms direct), Tier1 Phase 0 (after complexity assessment), Tier2 Phase 0 (after codebase analysis), Tier3 Phase 0 (after ticket analysis) — all via DevOps Agent (`Agent` delegation → `Bash` git checkout). Base: default branch.

**Lifecycle:** `Create → Work (all phases) → Merge → Delete` — DevOps creates at start, all work on branch, merge after human sign-off, delete after successful merge.

**Integration with Rollback:** Rollback safety nets (`backup/pre-<scope>-<timestamp>` + stash) work IN ADDITION to feature branch — they are snapshots on the feature branch.
```
feature/oauth2-login  (main working branch, entire workflow)
  ├── backup/pre-phase-1-20260831T120000  (snapshot before phase 1)
  ├── backup/pre-group-A-20260831T120000 (snapshot before parallel group A)
  └── stash: pre-phase-2 - auth-module   (fast restore)
```
Feature branch is NEVER reset/deleted during rollback. Only backup branches + stash are managed by rollback protocol.

## TDD Protocol — Spec → Test → Code (MANDATORY)

Every feature phase follows strict TDD with spec as single source of truth. Violating order blocks downstream phases.

### Sequence (per roadmap phase / feature)

1. **PM creates spec** — `docs/specs/<feature-slug>.md` with AC-N: GIVEN/WHEN/THEN. Spec status `approved` gates next step.
2. **PM delegates Test (FIRST)** — via Agent → Test Agent reads spec ACs and creates `tests/<slug>.*` stubs: `1 AC-N → 1 TC-00N`. Tests must initially FAIL (red). Verify with Glob that test file exists; coverage = TCs/ACs must be 100% before Developer starts.
3. **PM delegates Developer (SECOND)** — via Agent → Developer reads spec + tests and implements ONLY to make tests pass. No source before tests — if Glob for test file fails, Developer reports to PM and does NOT proceed.
4. **Test validates** — Test executes tests + regression suite via Bash. PASS → phase completes. FAIL → feedback loop (max 3 iterations).
5. **PM confirms phase** — Only after Test reports `PASS + 100% AC→TC coverage` does PM advance to next phase.

### AC Format

```markdown
### AC-1: User login
**GIVEN** valid user credentials
**WHEN** user submits login
**THEN** returns JWT token

### AC-2: Invalid credentials
**GIVEN** wrong password
**WHEN** user submits login
**THEN** returns 401 error
```
- One AC per behavior path. Separate ACs for alternative paths.
- GIVEN = preconditions, WHEN = actions, THEN = expected outcome

### Violations

- If Developer delegated without pre-existing tests → Developer reports missing test to PM, does NOT implement
- If Test creates tests not mapped to AC → reject; PM must first add AC to spec
- If spec AC modified after approval → Test regenerates tests, Developer re-implements

## File Integrity Checkpoints — Phase-Gate Verification

**Problem:** Downstream Agent may be delegated task requiring document never created → silent failure.

**Solution:** Before delegating any Agent, verify (Glob) all prerequisites exist. After delegation, verify deliverable exists with content >0. If missing → delegate recovery to responsible agent → re-verify → escalate to human after 2 failed attempts.

### Prerequisite & Deliverable Table

| Delegation | Verify BEFORE (prerequisites) | Verify AFTER (deliverable) | Recovery via |
|---|---|---|---|
| Tier 1 Ph 1 — PM: PRD + specs | — | `docs/PRD.md`, `docs/specs/*` (each spec has AC-N) | PM creates directly |
| Tier 1 Ph 1b — Test: TDD stubs (per spec) | `docs/specs/<slug>.md` (approved, AC format gate) | `tests/<slug>.*` + spec § Test Scenarios Mapping (100% AC→TC). Tests must FAIL (red) | Test |
| Tier 1 Ph 2 — Architect (Developer for Small): PLANNING + ROADMAP | `docs/PRD.md`, `docs/specs/*` | `docs/PLANNING.md` (M/L only) + `docs/IMPLEMENTATION_ROADMAP.md` with `status` per phase | Architect (M/L only; Small skip) |
| Tier 1 Ph 3 — Test: TDD stubs (per phase, if not done in 1b) | Relevant `docs/specs/<slug>.md` (approved) | `tests/<slug>.*` + mapping 100% AC→TC, tests FAIL | Test |
| Tier 1 Ph 3 — Developer: implementation (TDD) — grouped by `Parallel group` | `docs/specs/<slug>.md` + `tests/<slug>.*` (FAIL) + `docs/PLANNING.md` (if M/L) + `docs/IMPLEMENTATION_ROADMAP.md` with `Parallel group` + `status` | Source files for group + consolidated `docs/PROJECT_CONTEXT.md` (tests now PASS) — PM consolidates after group | Developer(s) in parallel per group |
| Tier 2 Ph 0 — PM: project context | — | `project_*` entity (only if Tier1 specs exist; else skip) | PM |
| Tier 2 Ph 1 — Architect: specs for feature | `project_*` if applicable | `docs/specs/<feature>.md` (SPEC template) | Architect |
| Tier 2 Ph 1b — Test: TDD stubs (feature) | `docs/specs/<feature>.md` (approved) | `tests/<slug>.*` + mapping 100% AC→TC, tests FAIL | Test |
| Tier 2 Ph 2 — Developer: implementation (TDD) | `docs/specs/<feature>.md` + `project_*` (if applicable) + `tests/<slug>.*` | Source + `docs/PROJECT_CONTEXT.md` (tests PASS) | Developer |
| Tier 1 Ph 5 — Documentation: final docs | `docs/PROJECT_CONTEXT.md` + source files | `docs/specs/*` synced (if Glob + git diff shows change) — M/L: + PLANNING §Decisions if changed; Large only: + docs/README.md + docs/API_REFERENCE.md | Documentation |
| Tier 1 Ph 6 — DevOps: commit | Phase 5 verified (Glob PASS; Small: specs sync verified or skipped) | `docs/CHANGELOG.md` derived + commit `git log -1` exists + `git status` clean | DevOps |
| Tier 2 Ph 5 — Documentation: specs sync | `docs/specs/*` exists + `docs/specs/<feature>.md` | `docs/specs/*` synced if git diff shows change | Documentation |
| Tier 2 Ph 6 — DevOps: commit | Phase 5 verified or skipped | commit + CHANGELOG derived | DevOps |
| Tier 3 Ph 5 — Documentation: specs sync | `docs/specs/*` exists (if Tier1 existed) | `docs/specs/*` synced if fix changed functionality | Documentation |
| Tier 3 Ph 6 — DevOps: commit | Phase 5 verified (Glob PASS) | commit `fix(... ) #<ticket>` + CHANGELOG | DevOps |
| Tier 3 Ph 0 — PM: ticket analysis | — | `ticket_*` entity (if MCP: search ticket_<number>) | PM |
| Tier 3 Ph 1 — Developer: root cause | `ticket_*` entity | `root_cause_*` entity (if MCP: search root_cause_<ticket>) | Developer |
| Tier 3 Ph 2 — Developer: bug-repro test + fix | `root_cause_*` | Bug-repro `tests/<slug>.*` (initially FAIL) → fix → test PASS + `docs/PROJECT_CONTEXT.md` | Developer |

### Recovery Protocol

1. Identify responsible agent from Document Ownership Map
2. Delegate recovery task with explicit context: document needed, why (downstream phase), any partial content, source docs to reference
3. Re-verify file exists and has content >0
4. Escalate to human if: recovery fails after 2 attempts, agent reports cannot create document, or missing document blocks critical phase

## Parallelization Protocol

> **PM MUST read this section before Tier1 Phase3 and before every finalization (Phases 5/6).** Do NOT delegate Developers or Documentation/DevOps without applying PM Execution Rules + PROJECT_CONTEXT.md Race Prevention below. Optimize Glob usage: batch independent Globs in parallel, use `docs/specs/*.md` not `**/*`, cache per phase.

When multiple modules/phases can be executed concurrently, use explicit parallelization markers.

### Parallel Group Markers in IMPLEMENTATION_ROADMAP.md

```markdown
### Phase 3a: Authentication Module (parallelizable)
- Files: src/auth/handler.go, src/auth/middleware.go
- Tests: tests/auth_test.go
- Dependencies: none
- Parallel group: A

### Phase 3b: API Endpoints (parallelizable)
- Files: src/api/routes.go, src/api/handlers.go
- Tests: tests/api_test.go
- Dependencies: none
- Parallel group: A

### Phase 3c: Database Layer (sequential)
- Files: src/db/repository.go, src/db/models.go
- Tests: tests/db_test.go
- Dependencies: 3a, 3b (needs auth + API interfaces)
- Parallel group: B

### Phase 4: Integration (sequential)
- Files: src/main.go
- Tests: tests/integration_test.go
- Dependencies: 3a, 3b, 3c
- Parallel group: C
```

**Marking Rules:** Analyze dependencies, group independent modules into A, B, C… Mark each with `Parallel group: <letter>`. Same group = parallel, different groups = sequential (respect dependencies).

**PM Execution Rules:** Read roadmap markers. If multiple phases share same group → launch ALL in single message (parallel Agent calls). Wait ALL to complete before next group. Never parallelize different groups. PROJECT_CONTEXT.md updates: each Developer reports changes to PM; PM consolidates after entire group completes (avoids race).

**PROJECT_CONTEXT.md Race Condition Prevention:** Parallel Developers do NOT write to PROJECT_CONTEXT.md directly — they report delta to PM in final report. After group completes, PM consolidates. Next sequential group can then begin.

## Rollback Protocol (Hybrid — Backup Branch + Stashpoint)

> **Single source of truth for rollback.** Hybrid model preserves BOTH safety nets: stash (fast) + branch (hard), unified naming `pre-<scope>` (`phase-<N>` or `group-<letter>`).

### Naming Convention (Unified — eliminates divergence)

- Sequential execution (Tier2 Phase2, Tier3 Phase2, Tier1 without parallel groups): `<scope> = phase-<N>` (e.g., phase-3, phase-2)
- Parallel-group execution (Tier1 Phase3 with `Parallel group: <letter>`): `<scope> = group-<letter>` (e.g., group-A, group-B)
- Backup branch: `backup/pre-<scope>-<timestamp>` (e.g., `backup/pre-phase-3-20260831T120000`, `backup/pre-group-A-20260831T120000`)
- Stashpoint message: `pre-<scope> - <name>` (e.g., `pre-phase-3 - auth-module`, `pre-group-A - auth+api`)

### Pre-phase Safety Net Creation (BEFORE Developer phase/group)

Before each Developer phase (Tier1 Phase3 / Tier2 Phase2 / Tier3 Phase2):
1. PM delegates to DevOps via Agent to create TWO safety nets with unified `<scope>`: branch `backup/pre-<scope>-<timestamp>` + stash `pre-<scope> - <name>` (`--keep-index --include-untracked`)
2. Verify both exist: `git branch --list "backup/pre-<scope>*"` + `git stash list` (message contains `pre-<scope>`)
3. If either fails → retry once; if still fails → escalate immediately — do NOT proceed without safety nets

### Post-phase Success (PASS)

After Test validates successfully for `<scope>`: resolve `STASH_REF=$(git stash list | grep "pre-<scope>" | head -1 | cut -d: -f1)` then `git stash drop "$STASH_REF"` + clean branch `git branch -d backup/pre-<scope>-<timestamp>` + verify both cleaned.

### Post-phase Failure (ROLLBACK)

If validation fails after max iterations:
1. Stop — do not proceed to next phase/group
2. Attempt fast restore (stash first): `git reset --hard HEAD` + `git stash pop --index` → verify `git status` + `git stash list`
3. If stash fails → fallback to backup branch: `git reset --hard backup/pre-<scope>-<timestamp>` → verify `git status` + `git log -1`
4. If backup fails → escalate immediately — do NOT attempt manual conflict resolution
5. Document rollback in `docs/CHANGELOG.md` with reason, branch name, reverted commits
6. Escalate — present to human for decision

### Post-Rollback Verification (MANDATORY)

After ANY rollback (stash pop or branch reset), verify restored state:
1. `git status` → clean working directory
2. Run ALL tests for complete scope (if rolling back group B, run tests for group A+B)
3. If ALL PASS → rollback successful; if ANY FAIL → fallback next method or escalate

Rules: Never proceed after rollback without verification; verification is part of rollback; if verification fails rollback is NOT complete; test scope = complete scope; escalate if both restore methods fail verification. Preferred restore is stash pop --index (fast, non-destructive); branch is fallback; never stash clear or reset --hard on main without PM approval.

## Knowledge Transfer Protocol

After workflow completion, ensure project state captured for future workflows:
1. Verify PROJECT_CONTEXT.md is current — Developer reviews/updates; PM verifies Glob exists + >20 lines
2. Verify specs are in sync — if specs exists, delegate Documentation to verify
3. Capture workflow learnings — after Tier1 Large or complex Tier2, create incident_* (if MCP: create_entities) with what worked, delays, coordination friction
4. Handoff summary — when starting new workflow on existing project: use memory search project_* + incident_workflow + Read PROJECT_CONTEXT.md + specs/ to inform planning

No separate document created. Knowledge lives in PROJECT_CONTEXT.md (state), incident_* in memory (learnings), specs/ (specifications).

## Token Budget Protocol

> Dogma: Token budgeting is OPTIONAL. PM asks at workflow start. Human decides. No auto-detection.

**Phase 0 — Budget Offer (MANDATORY via AskUserQuestion):**
```
"Do you want to set a token limit for this workflow? This helps prevent context window overflow."
Options: 100k tokens (Conservative) / 165k tokens (Standard window) / 262k tokens (Extended) / 500k tokens (Practically unlimited) / Custom value / No budget
```
If Custom: AskUserQuestion "Enter token limit (e.g., 200000):" → PM stores as token_budget. If No budget: do NOT monitor.

**Budget Monitoring (only if set):** PM tracks estimated consumption per delegation: agent role ~3-5k, workflow excerpt ~2-4k, spec/context ~3-8k, task description ~1-2k, total per delegation ~10-20k. Escalation: 70% note, 85% optimize prompts (shorter excerpts), 100% escalate via AskUserQuestion: "Keep current / Increase budget / Stop workflow". Store in workflow_* entity observations if MCP enabled: token_budget, tokens_consumed.

## Claude-Specific Notes

- **Agent tool vs task:** In Claude, PM delegates via `Agent` tool with `subagent_type` (architect, developer, test, code-review, devops, documentation, Explore). The skill `sdlc-workflow` (`.claude/skills/sdlc-workflow/SKILL.md`) provides the same Delegation Prompt Template adapted.
- **Tools:** Claude agents use `Read, Grep, Glob, Write, Edit, Bash, TodoWrite, Agent, WebSearch, WebFetch` — capitalized. OpenCode native `read/glob/grep/bash` map directly.
- **AskUserQuestion:** Claude equivalent of OpenCode `question`/`todowrite` prompt. Use for Tier 0 confirmation, complexity questions, token budget offer, human oversight points.
- **Glob optimization:** Same as OpenCode — batch independent Globs in parallel, use specific patterns (`docs/specs/*.md`, `tests/<slug>.*`) not `**/*`, cache per phase.
- **Bash approvals:** Claude Code manages via `settings.json` permissions + tool allowlist (same as OpenCode `bash: ask`). Test runners (`npm test`, `pytest`, `go test`, etc.) and read-only git commands pre-approved where possible.
