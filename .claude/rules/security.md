## Overview

This security policy applies to **every project** and is mandatory for all agents. Never remove or delete any file without explicit approval. Never expose sensitive credentials, tokens, keys, or secrets.

**Response**: *"I cannot access that file — it contains potentially sensitive credentials."*

### Sensitive Data Patterns

Any file containing these patterns should be treated as sensitive:
- Contains API keys, authentication tokens, or private keys
- Contains database connection strings with passwords
- Contains encryption keys or certificates
- Contains authentication credentials for any service

## Secret Patterns in Output (Redact or Refuse)

If tool output or file content contains these, **redact the secret portion** immediately:

| Pattern | Type | Action |
|---------|------|--------|
| `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_` + 36+ chars | GitHub tokens | Redact |
| `sk-` + 32+ chars | OpenAI keys | Redact |
| `xox[baprs]-` + 10+ chars | Slack tokens | Redact |
| `AKIA` + 16 uppercase chars | AWS keys | Redact |
| `-----BEGIN (RSA|EC|DSA|PRIVATE|OPENSSH) KEY-----` | Private keys | Redact entire block |
| `eyJ`...`.`...`....` (three base64 segments) | JWT tokens | Redact |
| `Authorization: (Bearer|Basic) ...` | Auth headers | Redact credential portion |

Additional: any string matching `*secret*`, `*key*`, `*credential*` in context of credentials; database connection strings with passwords; API keys embedded in code/config; certificates content.

Action: Redact with `[REDACTED]` placeholder and explain what was redacted.

## Blocked Commands (Never Execute or Suggest)

### Secret Loading Commands
| Command | Reason |
|---------|--------|
| `source .env`, `. ./.env`, `set -a; source .env` | Loads secrets into environment |
| `export $(grep -v '^#' .env \| xargs)` | Loads secrets into environment |
| `dotenv-cli`, `env-cli` | Loads secrets |

### Secret Redirection Commands
| Command | Reason |
|---------|--------|
| `cat .env \| ...`, piping `.env` anywhere | Redirection of secrets |
| `tail -f .env` | Redirection |
| Any command piping `.env` to stdout/network/files | Redirection |

### Network Exfiltration Commands
| Command | Reason |
|---------|--------|
| `curl/wget/nc` with Authorization header or token in URL | Exfiltration |
| `curl -d @.env`, `curl -d "$(env)"` | Exfiltration via HTTP |
| `curl -H "Authorization: Bearer TOKEN"` | Exfiltration |
| Any command sending credentials to external services | Exfiltration |

### Destructive Commands
| Command | Reason |
|---------|--------|
| `rm -rf`, `delete -all`, full directory deletion | Destructive |
| `truncate`, `wipe` | Destruction |
| `DROP TABLE`, `DELETE FROM` without WHERE | Destructive DB |
| Any command destroying data without explicit approval | Destructive |

Response: *"I cannot execute this command — it requires explicit approval for destructive operations."*

In Claude Code, these restrictions apply to `Bash` tool invocations. Even with Bash allowlist (`npm test`, `pytest`, `git status` etc.), never execute blocked commands.

## Destructive Side Effects Prevention

**NEVER create tests or scripts with destructive side effects:**

- **No destructive test creation:** Delete files/data as part of testing, modify production DB destructively, execute commands destroying system state, create scripts with side effects harming system
- **No destructive script creation:** Scripts with `rm`, `delete`, `drop` without explicit approval, modifying system state irreversibly
- **Safe testing required:** Tests must use isolated environments (temp files, test DB), have reversible side effects only, include rollback mechanisms if destructive needed, require explicit approval for destructive ops

Response: *"I cannot create a test or script with destructive side effects — it requires explicit approval and safe testing practices."*

**Approval Requirements for any destructive operation:**
1. Explicit approval from user
2. Safe environment (isolated, test first)
3. Rollback mechanism
4. Impact assessment

## Principles

1. **Least privilege:** never Read a file unless absolutely necessary
2. **Refuse by default:** when in doubt, refuse and explain
3. **No exfiltration:** never pipe sensitive content to network commands
4. **Redact over expose:** if secrets appear in safe output, redact secret portion
5. **No injection:** never write sensitive content to logs, stdout, or shared files
6. **Explicit approval for destruction:** Never delete/destroy without explicit user approval
7. **Safe testing required:** Tests must use isolated environments with reversible side effects
8. **Destructive operations require approval:** Any destructive Bash requires explicit approval
9. **Credential protection:** Never expose API keys, tokens, passwords, secrets
10. **Redact automatically:** Automatically redact sensitive content in output

## Model Bias Prevention for Security

Models tend to: create destructive tests (by deleting), execute dangerous commands (`rm -rf`) without consideration, expose credentials accidentally, ignore security policies as optional.

Counter by: always checking security policy before operation; never creating destructive tests without explicit approval; using isolated environments; including rollback mechanisms; explicitly asking for approval before destructive Bash; redacting automatically; treating security as mandatory not optional.

## Enforcement

Applies to every project, all agents (Project Manager, Developer, Test, Code Review, etc.), all operations (Read, Bash, Write), all output (tool results, file content, env vars).

When violated: immediate refusal, clear explanation, redact sensitive content, explicit approval required before proceeding.

## Compliance Checklist (before any operation)

- [ ] Does operation require reading sensitive file? → Refuse
- [ ] Does operation expose env vars? → Refuse
- [ ] Does operation contain secret patterns? → Redact
- [ ] Does operation execute blocked command via Bash? → Refuse
- [ ] Does operation create destructive test/script? → Refuse
- [ ] Does operation have destructive side effects via Bash/Write? → Require approval
- [ ] Does operation require explicit approval? → Ask user via AskUserQuestion

## Claude-Specific Notes

- **Settings:** Enforce via `.claude/settings.json` `permissions.allow` (`Read`, `Glob`, `Grep`, `WebSearch`, `WebFetch`, `TodoWrite`, `Bash` limited) plus per-agent `tools` lists. Keep `permissions.deny` updated for `Read(.env)`, `Bash(rm -rf)`, etc. if Claude Code supports deny patterns.
- **Read vs cat:** Never use `Bash(cat .env)` — use `Read` tool which also respects blocked files (model should refuse). Same for `.aws/`, `.ssh/` etc.
- **Bash piping:** Never `Bash` with `cat .env | curl` — blocked as exfiltration
- **Output redaction:** When `Read` or `Grep` or `Bash` output contains tokens matching patterns, redact to `[REDACTED]` before replying to user
