## Code Style & Simplicity (MANDATORY)

**Golden rule: default to the simplest possible solution.** Every line of code must justify its existence. Before adding *anything*, ask yourself:

> "Does the user explicitly need this? Or am I adding it out of habit / defensive programming / premature optimization?"

### Hard constraints (language-agnostic):
- ❌ **No unnecessary error handling** — handle errors only if the operation *will predictably crash* on valid inputs and the user asked for it. Don't guard against impossible failures.
- ❌ **No unnecessary type annotations** — add them only when the language requires them or the user explicitly requests them. Let the language's type inference work.
- ❌ **No unnecessary abstractions** — no classes, interfaces, traits, protocols, generics, factories, or design patterns unless they *obviously* simplify the code. A plain function is always better than a class/object/struct wrapper.
- ❌ **No unnecessary dependencies** — don't import libraries you don't use. Don't reach for a framework when the standard library suffices.
- ❌ **No logging frameworks** — `print`/`console.log`/`println`/`echo` is sufficient unless explicitly asked for.
- ❌ **No CLI frameworks** — don't add argument parsers, CLI builders, or command frameworks unless the user requests a CLI tool.
- ❌ **No config files** — don't create `.env`, config files, or settings modules unless required.
- ❌ **No unnecessary docstrings** — don't document trivial or private code whose purpose is obvious from its name and code. Public functions, classes, and APIs MUST have proper docstrings with purpose, parameters, return type, and a usage example.
- ❌ **No inline comments** — don't comment *what* the code does, only comment *why* when the reasoning isn't obvious.
- ❌ **No premature generalization** — don't make functions "flexible" for future use cases that don't exist yet. YAGNI (You Ain't Gonna Need It).

### Positive directives:
- ✅ **Prefer 3 clear lines over 30 robust lines.** Shorter is better.
- ✅ **Prefer declarative/functional style** over imperative mutation where natural (e.g., `map`/`filter` over manual loops, method chains over temporary variables).
- ✅ **Prefer standard library over third-party packages.** Don't reach for Lodash if `Array.map()` works. Don't install requests if `http.Get()` is enough.
- ✅ **Prefer functions over classes/objects.** A function is a unit of work; a class/struct is a unit of state. Use types only when you have state + behavior that belongs together.
- ✅ **Prefer returning early** over nested conditionals (guard clauses).
- ✅ **Name things what they are.** `users`, `getUser()`, `calculateTotal()`. No abbreviations, no Hungarian notation, no jargon.
- ✅ **One responsibility per function/method.** If it does two things, split it.
- ✅ **Write code that is obviously correct** over code that is "clever" or "idiomatic at the expense of clarity".
- ✅ **Prefer immutable data structures.**
- ✅ **Avoid duplicate code or logic.** When you detect it, report it with a suggestion for a refactor.
- ✅ **Avoid obsolete or deprecated technologies.**

### Anti-patterns to catch yourself:
- ❌ **Don't write a "robust" solution when a simple one works.** "Robust" is just "complex" in disguise.
- ❌ **Don't add a `main()` guard or argument parser** unless building a CLI tool.
- ❌ **Don't create a project structure** (`src/`, `tests/`, Makefile, etc.) for a single script.
- ❌ **Don't add configuration layers** (environment variables, config files, settings types) for hardcoded values.
- ❌ **Don't write "production-ready" code** unless the user explicitly asks for it.
- ❌ **Don't separate concerns prematurely** — a single file is fine until it's not.
- ❌ **Don't over-abstract** — no repository pattern for a single database call, no factory for a single class, no interface for a single implementation.
- ❌ **"What if the file/input doesn't exist?"** → only handle if the spec says so.
- ❌ **"Let me add a config for flexibility"** → YAGNI.
- ❌ **"I'll use library X for safety"** → the stdlib is fine.
- ❌ **"Let me structure this as a module"** → a single file is fine.
- ❌ **"I'll add error handling just in case"** → don't.
